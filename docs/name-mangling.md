# Quest C Name Mangling Specification

This document specifies the name mangling and symbol generation rules of the C backend
([`symbols.py`](../bootstrap/python/quest/codegen/symbols.py) and
[`layout.py`](../bootstrap/python/quest/codegen/layout.py), which every backend shares, and the C backend's
[`c/types.py`](../bootstrap/python/quest/codegen/c/types.py),
[`c/declarations.py`](../bootstrap/python/quest/codegen/c/declarations.py), and
[`c/printer.py`](../bootstrap/python/quest/codegen/c/printer.py)).

It serves as the definitive reference for understanding any symbol, struct, typedef, parameter, or temporary variable
generated during Quest C code generation (`codegen_c`).

---

## 1. Design Principles & Namespacing

The Quest compiler targets ISO C99 (`clang` / `gcc`). To ensure safe, collision-free code generation across translation
units, name mangling adheres to the following principles:

1. **C Keyword & Libc Protection:** Every Quest value and function identifier gets a prefix (`g_`, `l_`, `qf_`, or a
   module's `qv_<module>_`) to prevent collisions with C keywords (`int`, `return`, `default`, `static`, `register`,
   `case`, etc.) and standard library symbols (`open`, `read`, `write`, `exit`, etc.).
2. **C Struct Keyword Protection:** All Quest record field names inside C structs are prefixed with `qf_`
   (e.g. `qf_default`, `qf_return`) to allow arbitrary Quest field identifiers without colliding with C reserved words.
3. **Hierarchical Module Separation:** Module paths are flattened using double underscores (`__`), preventing collisions
   between different packages having identically named submodules (e.g. `util/path` $\rightarrow$ `util__path`).
4. **Deterministic Operator Mapping:** Symbolic operators are mapped to ASCII identifier segments via an unambiguous
   translation table prefixed with `qv_sym_`.
5. **Clear Linkage Boundaries:** Symbols are cleanly partitioned into `extern` (cross-module ABI), `static`
   (translation-unit internal), and local/block scopes.
6. **Header Shadowing Prevention:** Generated C interface headers keep the `.int` of their source's name (e.g.
   `string.int.h`, `path.int.h`) to prevent shadowing C standard library headers like `<string.h>`.

---

## 2. Linkage and Visibility Classification

Every C identifier generated by the compiler belongs to one of three linkage scopes:

| Linkage | Scope | C Storage Class | Examples | Description |
| :--- | :--- | :--- | :--- | :--- |
| **External** | Cross-unit | `extern` / default | `qm_util__path`, `qv_mod_calc_init`, `qv_calc_add` | Public module ABI & init |
| **Internal** | Translation unit | `static` | `qf_add`, `g_x`, `quest_type_Int` | Functions, globals, descriptors, dicts |
| **Local** | Function body | Automatic / stack | `l_x`, `_t1` | Variables, temporaries |

## 3. Value and Identifier Mangling

### 3.1. Alphanumeric Identifiers (`mangle_ident`)
`mangle_ident` prefixes a Quest identifier with `qv_`, converting any internal dot characters (such as qualified
names) to single underscores; the printer replaces the `qv_` with its own prefix for what it names (§5):

$$\text{mangle\_ident}(name) = \text{"qv\_"} + name.\text{replace}(".", "\_")$$

- `let x = 10` $\rightarrow$ `qv_x`
- `let count = 0` $\rightarrow$ `qv_count`
- `let default = true` $\rightarrow$ `qv_default` (safe from C keyword collision)
- `let point.x = 5` $\rightarrow$ `qv_point_x`

### 3.2. Symbolic Operators (`mangle_symbolic_ident`)
When symbolic operators appear as first-class functions or bindings, they are mangled using the prefix `qv_sym_`.
Each symbol character is looked up in `SYMBOL_MANGLE_MAP`:

| Character | Mangled Name | Character | Mangled Name | Character | Mangled Name |
| :---: | :--- | :---: | :--- | :---: | :--- |
| `+` | `plus` | `!` | `bang` | `^` | `caret` |
| `-` | `minus` | `?` | `question` | `&` | `amp` |
| `*` | `star` | `:` | `colon` | `\|` | `pipe` |
| `/` | `slash` | `@` | `at` | `~` | `tilde` |
| `=` | `equals` | `#` | `hash` | `\\` | `backslash` |
| `<` | `lt` | `$` | `dollar` | `'` | `prime` |
| `>` | `gt` | `%` | `percent` | `.` | Boundary / dot |

Runs of alphanumeric characters between symbols are preserved. Consecutive symbol names are joined with underscores:

- `+` $\rightarrow$ `qv_sym_plus`
- `++` $\rightarrow$ `qv_sym_plus_plus`
- `-` $\rightarrow$ `qv_sym_minus`
- `*` $\rightarrow$ `qv_sym_star`
- `:=` $\rightarrow$ `qv_sym_colon_equals`
- `<>` $\rightarrow$ `qv_sym_lt_gt`
- `->` $\rightarrow$ `qv_sym_minus_gt`
- `\=` $\rightarrow$ `qv_sym_backslash_equals`
- `<+>` $\rightarrow$ `qv_sym_lt_plus_gt`

## 4. Module & Library Names

Modules may be top-level or hierarchically nested within subdirectories.

### 4.1. Hierarchical Module Path Flattening (`mangle_module_name`)
Hierarchical module paths are canonicalized, converted to lowercase, with `/` mapped to `__` and `.` mapped to `_`.
The directory and file names in a canonical module path contain only letters and digits (`docs/modules.md` §2.3), so the
result is a valid C identifier fragment, and different paths differ after mangling except in case:

$$\text{mangle\_module\_name}(module) = module.\text{lower}().\text{replace}("/", "\_\_").\text{replace}(".", "\_")$$

- `calc` $\rightarrow$ `calc`
- `util/path` $\rightarrow$ `util__path`
- `collections/hashmap` $\rightarrow$ `collections__hashmap`
- `net/http/client` $\rightarrow$ `net__http__client`

### 4.2. Module Record Instance
Every compiled Quest module produces a single global `QRecordVal` holding its exported interface record:
- **Definition (in module):** `QRecordVal qm_<clean_mod>;`
  - E.g. `QRecordVal qm_calc;`, `QRecordVal qm_util__path;`
- **Import declaration (in consumers):** `extern QRecordVal qm_<clean_mod>;`
- Module records use their own `qm_` prefix rather than `qv_`: `qv_<clean_mod>` is also the mangling of a user
  identifier with the same name as the module (e.g. a top-level `let real` in a program that links module `real`).

### 4.3. Module Initialization Function & Guard
Each module defines an idempotent initialization function that initializes imported dependencies before evaluating
module-level bindings:
- **Init function:** `void qv_mod_<clean_mod>_init(void);`
  - E.g. `void qv_mod_calc_init(void);`, `void qv_mod_util__path_init(void);`
- **Consumer declaration:** `extern void qv_mod_<clean_mod>_init(void);`
- **Internal initialization flag (static):**
  - `static bool qv_mod_<clean_mod>_initialized = false;`

### 4.4. Module Exported Functions (`mangle_module_ident`)
A module file exports a C function for each member of its interface that is a function or a polymorphic value, which
importers call directly (`module_function_signature` in `c/declarations.py`):
- **Alphanumeric:** `qv_<clean_mod>_<name>`
  - E.g. `qv_calc_add`, `qv_util__path_join`
- **Symbolic operator:** `qv_<clean_mod>_sym_<parts>`
  - E.g. `qv_int_sym_plus`

The module's own functions and values are internal, named as a program's are (§5).

### 4.5. Module Payload Pointer
During module initialization, the record payload is populated via a local typed pointer, `_payload`.

### 4.7. Interface C Header Files
To avoid collision with C runtime and system headers (e.g. `<string.h>`):
- **Pattern:** `<interface_stem>.int.h`, included by its canonical path (e.g. `#include "util/path.int.h"`)
  - E.g. `string.int.h`, `path.int.h`, `calc.int.h`
- Module C sources likewise keep the `.mod` of their source's name: `<module_stem>.mod.c`.

## 5. Functions, Closures, & Specializations

### 5.1. Functions
Every function of a unit, lifted by closure conversion, is a static C function named for its variable, prefixed
with `qf_` (with a suffix when two share a name):
- **Pattern:** `static <return_type> qf_<name>(void *_raw_env, <descriptors>, <params>)`
  - E.g. `static QInt qf_factorial(void *_raw_env, QInt l_n)`
- **Anonymous functions:** `qf_f`, `qf_f_2`, ...
- **Specialized clones:** named for the clone's variable, `<name>_spec`: e.g. `qf_map_spec`, `qf_map_spec_2` (a
  module's clones are its members `<name>_spec<n>`, so `qf_map_spec1`).

### 5.2. Closures
- **Environment structure:** `struct QEnv_<function>`, with descriptor fields `d<i>` and captures `c<i>`
  - E.g. `struct QEnv_qf_h { QInt c0; };`
- **Environment pointer:** the function's environment variable, `(struct QEnv_<function> *)_raw_env`.
- **Static closure:** every function has one, used when it captures nothing:
  - `static Q_UNUSED QClosure qf_<name>_closure = { (void *)qf_<name>, NULL };`

### 5.3. Variables
- **Globals** (what the top levels bind outside loops): `static <type> g_<name>;`
- **Locals:** `l_<name>`

### 5.4. Thunks and Adapters
- **Closure adapters** (`adapt` plans): `qa_adapt`, `qa_adapt_2`, ...
- **Type applications:** `qa_type_app`, with environment struct `QTypeAppEnv_qa_type_app`
- **External C functions as closures:** `qx_<symbol>`, with static closure `qx_<symbol>_closure`
- **Function type descriptor and adapter:** `quest_type_fun_<digest>`, `quest_adapt_fun_<digest>`, and its thunk
  `quest_thunk_fun_<digest>`, where `<digest>` is 16 hex digits of a SHA-256 of the function type's text
- **Record offset table registration:** `qr_register_dicts`

## 6. Types, Aggregates, & Fields

### 6.1. Record Structs and Fields
- **Record struct tag:** `struct QT_<name>` (managed by `RecordNamingContext`; records share a struct only if their
  fields have the same names and types, which also makes their descriptors distinct):
  - Aliased records: `struct QT_<TypeName>_<digest>` (e.g. `struct QT_Point_3f1c0a9e5b7d2468`)
  - Anonymous / structural records: `struct QT_record_<digest>`
  - `<digest>` is 16 hex digits of a hash of the record's field names and types, so a name stands for one layout in
    every C unit: interface headers define record structs under include guards named after them, and one unit
    includes headers generated in other compilations.
  - Structural fallback: `struct QRecord_<fld1>_<t1>_<fld2>_<t2>`
- **Record Header:** All record structs start with `QRecordHeader header;` (storing the descriptor of the record's layout).
- **Record Field Mangling:** Every record field name is prefixed with `qf_`:
  - `qf_<field_name>`
  - E.g. `qf_x`, `qf_name`, `qf_default`, `qf_return`
  - Field access in C: `rec->qf_x` or `payload->qf_name`

### 6.2. Tuple Structs and Fields
- **Tuple struct tag:** `struct QTuple_<type1>_<type2>...`
  - E.g. `struct QTuple_Int_String`, `struct QTuple_Int_Int_Bool`
  - A component that is itself a tuple, record, variant, option, or auto type has its tag closed with `_end`, so
    that different nestings get different tags: `Tuple (Tuple A Int) end` is `QTuple_QTuple_QVal_Int_end` and
    `Tuple (Tuple A) Int end` is `QTuple_QTuple_QVal_end_Int`. The same holds inside record, variant, option, and
    array tags.
- **Tuple Fields:** Positional 0-indexed fields:
  - `_0`, `_1`, `_2`, ...
  - Access in C: `tup._0`, `tup._1`

### 6.3. Variant Structs and Union Branches
- **Variant struct tag:** `struct QVariant_<tag1>_<type1>_<tag2>_<type2>...`
  - E.g. `struct QVariant_leaf_Int_node_QVal`
- **Variant Members:**
  - `int64_t tag;`
  - `union { ... } u;`
- **Payload struct tags:** `struct <variant_tag>_<case_name>_payload`

### 6.4. Option Structs and Union Branches
- **Option struct tag:** `struct QOption_<tag1>_<type1>_<tag2>_<type2>...`
  - E.g. `struct QOption_none_some_Int`
- **Option Members:**
  - `int64_t tag;`
  - `union { ... } u;` with nested branch structs containing payload `val` or `qf_<field>`.

### 6.5. Subtyping Evidence Dictionaries
Quest supports Cardelli record width and depth subtyping via static offset dictionaries passed in fat pointers:
- **Dictionary struct type:** `struct OffsetDict_<record_name>` (typedef `OffsetDict_<record_name>`)
  - Members: `size_t offset_<field_name>;`
  - E.g. `struct OffsetDict_record_<digest> { size_t offset_x; size_t offset_y; };`
- **Static dictionary instance:**
  - `static const OffsetDict_<target> offsetdict_<target>_<source> = { offsetof(...), ... };`
  - E.g. `static const OffsetDict_record_<d1> offsetdict_record_<d1>_record_<d2> = { offsetof(struct QT_record_<d2>, qf_x), ... };`

### 6.6. Variant Tag Remapping Tables
When a variant is coerced to a supertype variant:
- **Static remapping array:**
  - `static const int64_t tagmap_<tgt_tag>_<src_tag>[<case_count>] = { ... };`

### 6.7. Tuple Layout Assertions
Tuple structural subtyping is verified at compile time with C11/C99 static assertions:
- **Static assertion identifier:** `tuple_coercion_<tgt>_<src>_<index>`

### 6.8. Runtime Type Descriptors
Dynamic typing and existential ADTs utilize runtime descriptors:
- **Global descriptor instance:** `static const QTypeDescriptor quest_type_<tag>`
- **Record descriptor:** `static const QRecordTypeDescriptor qrec_desc_<tag>`
- **Tuple descriptor:** `qtup_desc_<tag>`
- **Variant / Option descriptor:** `qvar_desc_<tag>`

## 7. Parameters and Generated Temporaries

### 7.1. Function Parameters
- **Normal parameters:** the parameter's variable, `l_<param_name>` (e.g. `l_x`, `l_len`)
- **Module function export parameters:** `qv_p_<param_name>` (e.g. `qv_p_a`, `qv_p_b`)
- **Type descriptor parameters (polymorphic descriptors):** `descriptor_<quantifier_name>` (e.g. `descriptor_T`)
- **Thunk parameters:** `qa_<index>` and descriptors `qd_<index>`; function type adapters' `qv_arg_<index>`

### 7.2. Temporaries
The IR names every intermediate value, so most are variables (`l_t`, `l_t_2`, ...). The printer's own temporaries,
for what it allocates while printing one operation (an environment, a closure, a tuple being converted), are `_t<n>`,
declared at the function's start. Exception handlers are `_qh`, `_qh_2`, ...
